# ADR-000 — Arquitetura do Sistema de Fluxo de Caixa Diário

- **Status:** Aceito
- **Data:** 2026-10-29
- **Autor:** Kleber Augusto
- **Decisores:** Arquiteto de Soluções, Tech Lead, Product Owner
- **Contexto do desafio:** Desafio de Arquitetura de Soluções — controle de lançamentos e consolidação diária de saldo

---

## 1. Contexto

Um comerciante precisa controlar o fluxo de caixa diário com lançamentos
(débitos e créditos) e consultar um relatório de saldo diário consolidado.

O enunciado impõe um requisito de disponibilidade que define toda a arquitetura:

> *"O serviço de controle de lançamento não deve ficar indisponível se o sistema
> de consolidado diário cair."*

E um requisito de carga que define o dimensionamento:

> *"Em dias de picos, o serviço de consolidado diário recebe 50 requisições por
> segundo, com no máximo 5% de perda de requisições."*

A leitura correta desses dois requisitos juntos é o que separa uma solução
correta de uma solução que apenas parece correta:

1. **Isolamento de falha é obrigatório, não desejável.** Se o desenho permite que
   a indisponibilidade do consolidado propague para o lançamento, a solução está
   errada — independentemente de quão elegante seja o resto.
2. **5% de perda é o teto tolerado, não a meta.** O desenho precisa garantir que
   os 95% cheguem mesmo sob falha parcial. Isso exclui qualquer caminho crítico
   que dependa de HTTP síncrono entre os serviços.
3. **O saldo pode ser eventualmente consistente.** Fluxo de caixa diário não é
   um sistema de autorização de pagamento. Uma janela de consolidação de
   centenas de milissegundos é aceitável; bloquear a escrita para garantir
   consistência forte, não é.

### Forças em jogo

| Força | Direção |
|---|---|
| Disponibilidade do lançamento | Deve ser máxima, independente do consolidado |
| Consistência do saldo | Pode ser eventual |
| Auditabilidade | Deve ser total e imutável |
| Complexidade operacional | Deve ser proporcional ao volume (~50 msg/s) |
| Custo | Deve ser baixo; sem licenças proprietárias |
| Escalabilidade | Deve suportar pico sem degradação significativa |

---

## 2. Decisão

Adotar **microsserviços com integração assíncrona via broker, usando o padrão
Transactional Outbox no serviço de lançamentos**, com dois serviços
independentes e bancos separados:

| Serviço | Responsabilidade | Fonte da verdade |
|---|---|---|
| **Ledger API** | Controle de lançamentos | ✅ Sim |
| **Consolidation API** | Saldo diário consolidado | ❌ Projeção derivada |

### Decisões estruturais que compõem esta ADR

| # | Decisão | ADR filha |
|---|---|---|
| D1 | Dois microsserviços independentes, bancos separados | ADR-001 |
| D2 | Transactional Outbox para publicação confiável | ADR-001 |
| D3 | RabbitMQ em vez de Kafka | ADR-002 |
| D4 | PostgreSQL para ambos os serviços | ADR-003 |
| D5 | Ledger append-only com estorno | ADR-004 |
| D6 | Idempotência em duas camadas | ADR-005 |
| D7 | Cache read-through com TTL de 30s | ADR-006 |

## 3. Arquitetura Alvo

### 3.1 Visão de componentes

```
┌──────────────────────────────────────────────────────────────────┐
│                        CLIENTE (Comerciante)                     │
└───────────────┬──────────────────────────────┬───────────────────┘
                │ POST /entries                │ GET /balances
                ▼                              ▼
   ┌────────────────────────┐      ┌────────────────────────────┐
   │  LEDGER API            │      │  CONSOLIDATION API         │
   │  Domain (Entry)        │      │  Query (cache-first)       │
   │  Application           │      │  Consumer (idempotente)    │
   │  Infrastructure        │      │  Infrastructure            │
   └───────────┬────────────┘      └─────────────┬──────────────┘
               │                                 │
     ┌─────────┴──────────┐            ┌─────────┴──────────┐
     │ PostgreSQL         │            │ PostgreSQL         │
     │  entries           │            │  daily_balances    │
     │  outbox_messages   │            │  processed_events  │
     └─────────┬──────────┘            └─────────▲──────────┘
               │                                 │
     Outbox Relay (BackgroundService)            │
               │                                 │
               ▼                                 │
     ┌───────────────────────────────────────────┴──────┐
     │            RabbitMQ                              │
     │   queue: cashflow.entry.registered               │
     │   DLQ  : cashflow.entry.registered.dlq           │
     └──────────────────────────────────────────────────┘
               │
               ▼
     ┌──────────────────────────┐
     │  Prometheus + Grafana    │
     │  OpenTelemetry           │
     └──────────────────────────┘
```

### 3.2 Fluxo de escrita (lançamento)

```
1. Cliente → POST /api/v1/entries  (Idempotency-Key: <uuid>)
2. Ledger valida → cria Entry
3. INSERT entries + INSERT outbox_messages  ── MESMA TRANSAÇÃO
4. Commit atômico → 201 Created
5. Outbox Relay (poll 500ms) lê pendentes e publica no RabbitMQ
6. Relay marca published_at
```

O passo 3 é a decisão central. Se o evento fosse publicado direto no broker sem
o outbox, existiria uma janela em que o commit falha e o evento já foi publicado
(consolidado à frente do ledger) ou em que o publish falha e o commit passou
(lançamento perdido silenciosamente). O outbox elimina essa janela.

### 3.3 Fluxo de leitura (consolidado)

```
1. Cliente → GET /api/v1/balances/{date}
2. Consolidation → Redis (cache hit? retorna)
3. Miss → PostgreSQL daily_balances
4. Popula cache (TTL 30s) → retorna
```

### 3.4 Fluxo de falha — consolidado indisponível

```
Consolidation fora do ar
        │
        ├─ Ledger: 100% operante (nunca chama o consolidado)
        ├─ Eventos acumulam no RabbitMQ (durável, persistido em disco)
        └─ Ao voltar: consumer drena o backlog
                      ├─ dentro do retry → processa normalmente
                      └─ excede retries → DLQ (nada é perdido)
                                                │
                              operador roda POST /api/v1/balances/reconcile
                              que recalcula do Ledger (fonte da verdade)
```

**Este é o diagrama que responde literalmente ao requisito obrigatório.** A
reconciliação lê de `entries`, não do broker — funciona mesmo com fila perdida.

## 4. Modelo de Domínio

### 4.1 Bounded Contexts

| Contexto | Tipo | Agregado raiz | Responsabilidade |
|---|---|---|---|
| **Ledger** | Core | `Entry` | Verdade absoluta das movimentações |
| **Consolidation** | Core | `DailyBalance` | Projeção derivada, reconstruível |
| **Identity** | Generic | `Merchant` | Tenancy e autorização |

O Consolidation **nunca** é fonte da verdade. É integralmente reconstruível a
partir do Ledger — é isso que torna o desacoplamento de disponibilidade possível
e a reconciliação viável.

### 4.2 Linguagem ubíqua

| Termo | Definição |
|---|---|
| `Entry` | Lançamento imutável. Positivo = crédito, negativo = débito |
| `Reversal` | Entry que anula outra via `reversesEntryId` |
| `DailyBalance` | Soma líquida das entries de um comerciante em um dia |
| `CorrelationId` | Rastreia a requisição por todo o sistema |
| `IdempotencyKey` | Impede duplicidade de um mesmo lançamento |

### 4.3 Regras de negócio

| ID | Regra | Justificativa |
|---|---|---|
| **RN-01** | Lançamentos são append-only; estorno é novo lançamento de sinal oposto | Trilha de auditoria imutável; reconciliação determinística |
| **RN-02** | Consolida pela data de competência (`occurredOn`), não pela data de processamento | Pico às 23:59 não deve jogar lançamento para o dia seguinte |
| **RN-03** | Débito é valor negativo; não existe enum `Debit`/`Credit` | `saldo = SUM(amount)` não pode ser implementado errado |
| **RN-04** | Arredondamento com `MidpointRounding.ToEven` (2 casas) | Evita viés sistemático que aparece como divergência de centavos |
| **RN-05** | `Idempotency-Key` obrigatório na criação | Retry de rede não pode duplicar lançamento |
| **RN-06** | Tenant sempre vem do token, nunca do corpo da requisição | Impede IDOR entre comerciantes |

## 5. Requisitos

### 5.1 Funcionais

| ID | Requisito | Serviço |
|---|---|---|
| RF-01 | Registrar lançamento (débito/crédito) | Ledger |
| RF-02 | Consultar lançamento por id | Ledger |
| RF-03 | Listar lançamentos por período | Ledger |
| RF-04 | Estornar lançamento | Ledger |
| RF-05 | Publicar evento `EntryRegistered` | Ledger |
| RF-06 | Manter saldo diário por comerciante | Consolidation |
| RF-07 | Consultar consolidado de um dia | Consolidation |
| RF-08 | Consultar consolidado por intervalo | Consolidation |
| RF-09 | Reprocessar período (reconciliação) | Consolidation |
| RF-10 | Idempotência na recepção de eventos | Consolidation |

### 5.2 Não funcionais

| ID | Requisito | Meta | Mecanismo |
|---|---|---|---|
| RNF-01 | Lançamentos disponível com Consolidado fora | 99,95% | Broker desacoplado + outbox |
| RNF-02 | Consolidado suporta pico | 50 req/s | Prefetch 32 + 4 consumidores |
| RNF-03 | Perda máxima no pico | ≤ 5% | Retry exponencial + DLQ + backpressure |
| RNF-04 | Latência consulta consolidado | p95 < 150 ms | Redis + índice composto |
| RNF-05 | Latência escrita lançamento | p95 < 200 ms | Escrita local + outbox |
| RNF-06 | Segurança no consumo | — | JWT RS256 + claim `merchant_id` + mTLS |
| RNF-07 | Observabilidade | — | OpenTelemetry + Prometheus + Grafana |
| RNF-08 | Recuperação de falha | RPO ≈ 0, RTO < 5 min | Outbox + replicação Postgres |
| RNF-09 | Auditabilidade | 100% | Event log imutável |

### 5.3 Dimensionamento para 50 req/s

A conta que importa: 50 req/s × 5% = **2,5 req/s de tolerância**.

- Throughput necessário: 50 msg/s × ~1 KB ≈ **50 KB/s** — trivial para RabbitMQ.
- O gargalo real **não** é volume, é **contenção**:
  1. **Prefetch 32 + 4 consumidores concorrentes** — ~8,3 msg/s por consumidor.
  2. **UPSERT atômico** (`ON CONFLICT DO UPDATE`) em vez de read-modify-write.
     Sem isso, requisições concorrentes no mesmo dia geram deadlock e os 5% viram 30%.

## 6. Stack Tecnológica

| Camada | Tecnologia | Justificativa |
|---|---|---|
| Runtime | .NET 8 / C# 12 | Performance, Minimal APIs, ecossistema maduro |
| API | ASP.NET Core Minimal APIs | Startup rápido, pouca cerimônia |
| ORM | EF Core 8 | Migrations, LINQ type-safe, SQL nativo para UPSERT |
| Banco | PostgreSQL 16 | ACID, `ON CONFLICT`, `jsonb`, custo zero |
| Mensageria | RabbitMQ 3.13 | DLQ nativa, management UI, baixo custo operacional |
| Cliente de mensageria | MassTransit | Retry, DLQ, redelivery, observabilidade |
| Cache | Redis 7 | Cache read-through do consolidado |
| Observabilidade | OpenTelemetry + Prometheus + Grafana | Padrão de mercado, sem lock-in |
| Testes | xUnit + FluentAssertions + Testcontainers | Domínio + integração real |
| Infra local | Docker Compose | Um comando sobe tudo |

**Licenças: USD 0.** Toda a stack é open source — o custo é integralmente de
infraestrutura, sem vendor lock-in.

## 7. Alternativas Consideradas

| Alternativa | Por que foi rejeitada |
|---|---|
| **Monolito modular** | Não demonstra o isolamento exigido pelo RNF-01. Um processo = uma falha derruba tudo. |
| **Serverless** | Consolidado a 50 req/s com estado por dia e cache quente — cold start e limite de conexão a banco jogam contra. Custo imprevisível. |
| **Microsserviços REST síncrono puro** | Acoplamento temporal. Se o consolidado cai, o lançamento cai. Viola RNF-01 diretamente. |
| **Publicar direto no broker (sem outbox)** | Janela de inconsistência entre commit e publish. Divergência silenciosa. |
| **Kafka em vez de RabbitMQ** | Overkill para 50 msg/s. Custo operacional maior sem benefício proporcional. |
| **CQRS com event store dedicado** | Correto na direção, mas complexidade desproporcional ao escopo. Registrado como evolução futura. |
| **Microsserviços + Outbox + Broker** ✅ | **Escolhida.** Desacoplamento temporal real, isolamento de falha verificável, replay nativo. |

## 8. Consequências

### Positivas

- **Isolamento de falha real**, verificável em teste: derrubar o consumer não
  afeta o Ledger.
- **Replay e reconciliação nativos** — o Consolidation é reconstruível do zero.
- **Consistência eventual com janela mensurável** (centenas de ms em regime normal).
- **Nenhum evento perdido** em falha de broker (RPO ≈ 0).
- **Custo de licença zero**, sem vendor lock-in.
- **MassTransit permite trocar transporte** (RabbitMQ → Kafka) sem reescrever a aplicação.

### Negativas

- **Complexidade operacional maior** que um monolito: mais um cluster, mais deploy.
- **Cliente vê o saldo com latência de consolidação** — aceitável para fluxo diário.
- **`outbox_messages` e `processed_events` crescem** — exigem job de limpeza
  (registrado em evoluções futuras).
- **Ordenação por comerciante** exige particionamento; hoje fila única.

### Riscos e mitigações

| Risco | Mitigação |
|---|---|
| Deadlock no UPSERT sob concorrência | `ON CONFLICT DO UPDATE` atômico |
| Duplicidade por reentrega do broker | `processed_events` com `event_id` como PK |
| Duplicidade por retry do cliente | `Idempotency-Key` com índice único composto |
| Broker fora por tempo prolongado | Outbox retém o evento; reconciliação após retorno |
| Divergência entre ledger e consolidado | Endpoint de reconciliação recalcula do ledger |
| Staleness do cache | TTL de 30s; consolidação já é eventual |

## 9. Critérios de Aceitação

A solução está correta quando:

1. **Derrubar o Consolidation** e registrar um lançamento retorna `201` — o
   Ledger não foi afetado.
2. **Reiniciar o Consolidation** faz o lançamento aparecer no saldo consolidado.
3. **Repetir o mesmo `POST /entries`** com a mesma `Idempotency-Key` retorna o
   lançamento original, sem duplicar.
4. **Reentregar o mesmo evento** ao consumer não duplica o valor no saldo.
5. **`ON CONFLICT DO UPDATE`** sustenta 50 escritas concorrentes no mesmo dia
   sem deadlock.
6. **Estornar** cria um novo lançamento e o original permanece intacto.

### Teste de aceitação do requisito crítico

```bash
docker compose stop consolidation-api
curl -X POST http://localhost:5081/api/v1/entries \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"amount": 100.00, "occurredOn": "2026-10-29", "description": "Teste"}'
# Esperado: 201 Created

docker compose start consolidation-api
sleep 2
curl http://localhost:5082/api/v1/balances/2026-10-29
# Esperado: balance = 100.00
```

## 10. Pontos de Extensão e Evolução

Transparência sobre o que não está nesta entrega:

### Curto prazo (bloqueiam produção)

1. **Testcontainers nos testes de integração** — os testes atuais validam
   intenção, não SQL real.
2. **Autenticação JWT completa** — o código lê o claim `merchant_id` mas não
   configura `AddAuthentication/JwtBearer`.
3. **Endpoint `POST /api/v1/balances/reconcile`** — essencial para recuperação.

### Médio prazo

4. Job de TTL em `processed_events` e `outbox_messages`.
5. Particionamento por `merchantId` (Kafka com `PartitionKey`).
6. Rate limiting no gateway — mecanismo que realmente garante o RNF-03.
7. Teste de carga com k6/NBomber a 50 req/s — prova numérica do RNF-02.

### Longo prazo

8. Event sourcing completo com event store dedicado.
9. Multi-moeda com isolamento físico por tenant.
10. Fechamento contábil mensal com snapshot imutável.
11. API GraphQL/BFF para dashboards.
